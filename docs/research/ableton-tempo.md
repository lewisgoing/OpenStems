# Ableton ignores embedded tempo; ship a Set instead

> **Tested 2026-11-24 in Live 13 beta** (ADR 0016, "Ableton Live"): Live ignores the `acid`
> chunk with auto-warp on and off; it put bar 1 at the start of every file and read a bass
> stem at 1.5 times the tempo. The test files come from `scripts/make_ableton_test_files.py`
> (`uv run python ../scripts/make_ableton_test_files.py FOLDER` in `engine/`). What follows is
> the desk research from before the test.

Ableton Live does not read the tempo that OpenStems embeds in its WAV stems. Ableton's own help center says the ACID loop tags in WAV files "can not be used in Live", and sample vendors and forum reports agree that Live treats an ACIDized WAV as a plain WAV and runs its own analysis ([Ableton Help](https://help.ableton.com/hc/en-us/articles/115001134410-Supported-sample-formats); [Mode Audio](https://modeaudio.com/support)). So neither the acid chunk's tempo nor its beat count does anything in Live, and setting the beat count to N instead of 0 would not change that. No source shows Live taking tempo from any other embedded source either: BWF/iXML, ID3 TBPM, FLAC/Vorbis tags or the file name. The only per-file warp data Live honors is its own `.asd` analysis file, a proprietary binary that changed format by Live 12 and that no third party has learned to write. The practical consequence for OpenStems is clear. Keep the acid chunk, which is harmless in Live and needed for FL Studio. Tell Live users the one manual step that works: set the Set's tempo to the song's BPM, then fix bar 1. If OpenStems wants stems to open in Live already on the grid, the realistic route is a generated `.als` Live Set. It is gzipped XML that can carry the song tempo and per-clip warp markers, and OpenStems already knows the tempo and bar 1 for each song. No published hands-on test of an ACIDized WAV in Live 11 or 12 exists, and the key Ableton quote comes from a search snippet because the page refused automated fetches, so a ten-minute test in Live 12.4 should confirm the headline before any user-facing text relies on it.

## Live ignores the acid chunk and every other tempo tag

The strongest evidence is Ableton's own "Supported sample formats" article. It says ACID loops "are .wav files that contain additional ACID loop tags which, however, can not be used in Live". It says the same of Apple's Soundtrack loop tags in AIFF: "Live can not use specific Soundtrack loop tags" ([Ableton Help](https://help.ableton.com/hc/en-us/articles/115001134410-Supported-sample-formats)). That page returned HTTP 403 to the research fetches, so the quote comes from search-result snippets. Its source is still the vendor's current help page. Mode Audio, a sample vendor, is blunter: **"Ableton Live cannot read the TCE information in Acid WAVs, and so treats the files as regular wave (.wav) files"**, and Live "does however perform its own high quality note onset analysis when you import" ([Mode Audio](https://modeaudio.com/support)). Ableton forum threads from the Live 2 to 4 era report the same, and one 2002 thread is a feature request for ACID support ([Ableton Forum](https://forum.ableton.com/viewtopic.php?t=17537); [Ableton Forum](https://forum.ableton.com/viewtopic.php?t=1412)). The only counter-claim is a hedged 2019 KVR post ("I think … Ableton Live loads acid wavs, but I'm not 100% sure") with no source behind it ([KVR](https://www.kvraudio.com/forum/viewtopic.php?t=535182)). Other DAWs do differ. Mode Audio lists Cubase as using the ACID data, and Pro Tools as using it only through its Workspace browser ([Mode Audio](https://modeaudio.com/support)). Live is the odd one out, not the rule.

Nothing in recent releases changes this. The Live 12 release notes through 12.4 (May 2026) and the Live 13 beta notes through 13.0b26 (18 November 2026) contain no item on ACID, WAV chunks or tempo metadata on import ([Live 12 release notes](https://www.ableton.com/en/release-notes/live-12/); [Live 13 beta release notes](https://www.ableton.com/en/release-notes/live-13-beta/)). Live 13's beta goes the other way. It adds export of a tempo map as a MIDI file, which "encodes all tempo and time signature changes over the exported audio range" and is meant to travel beside unwarped audio. That suggests Ableton's own answer to "carry tempo with audio" is a sidecar file, not a chunk.

Other formats fare the same, with one exception. REX files load in a dedicated REX warp mode at the Set tempo ([ManualsLib, Live manual](https://www.manualslib.com/manual/449421/Ableton-Live.html?page=135); [Cycling '74 LOM Clip](https://docs.cycling74.com/apiref/lom/clip/)). Live can't read the stretch data in Apple Loops, and it never supported CAF ([Mode Audio](https://modeaudio.com/support); [Ableton Forum](https://forum.ableton.com/viewtopic.php?t=185667)). No source, for or against, mentions BWF bext or iXML, ID3 TBPM, or FLAC/Vorbis BPM comments. The Live 12 manual chapters on warping and file management name no metadata that Live reads on import ([Live 12 manual: warping](https://www.ableton.com/en/manual/audio-clips-tempo-and-warping/); [Live 12 manual: files](https://www.ableton.com/en/live-manual/12/managing-files-and-sets/)). Treat these as not read, though that rests on silence, not a statement. A tempo in the file name is a human aid only. Warping guides tell users to read "Drums_124bpm" from the name and type the number into the BPM field when Live guesses wrong, which shows Live doesn't apply it itself ([mixelite](https://mixelite.com/blog/warp-tracks-ableton-live/)). Splice samples in Live 12.3 do arrive tempo-locked, with Warp on and "a Warp Marker … placed at the very start of the file". That path runs through Live's built-in Splice integration, and an outside file can't use it ([Splice support](https://support.splice.com/en/articles/12062819-using-warp-and-timestretch-with-splice-in-ableton-live-12-3)).

## Every OpenStems stem goes down Live's long-sample auto-warp path

On import Live sorts each sample into "short" or "long" and applies the matching preference ([Live 12 manual](https://www.ableton.com/en/manual/audio-clips-tempo-and-warping/)). Ableton documents no length threshold. Short samples follow "Loop/Warp Short Samples", whose default is Auto. For an even-length loop Live "assumes that it contains a well-cut musical loop of 1, 2, 4, 8, or 16 bars in length, and sets the tempo accordingly". It then places one warp marker at the start and one at the end. A full-length stem is never short, so it follows the long-sample preference. That preference is on by default and is called "Auto-Warp Long Samples" in the manual's text and "Auto-Warp Long Files" in CDM's menu path; the Live 12 Settings wording was not checked ([CDM](https://cdm.link/live-11-3-10-auto-warp/)). With it on, Live runs its own tempo and beat analysis. With it off, **"long samples will be unwarped when they are added to tracks"**. The estimate appears in the BPM field and can be off by a factor of two ([Live 12 manual](https://www.ableton.com/en/manual/audio-clips-tempo-and-warping/)).

What auto-warp produces depends on the version. Before Live 11.3.10, a long sample got a warp marker on the first beat of each bar. Live 11.3.10 (August 2023) changed the algorithm. It places the downbeat more accurately, maps tempo changes on its own, and usually gives steady-tempo material **a single warp marker and a fixed tempo**. Clips already analyzed need "Warp From Here" to re-run ([CDM](https://cdm.link/live-11-3-10-auto-warp/)). Live 12.3 added built-in stem separation. It also lets "Set 1.1.1 Here" act on several audio clips at once, but only when they have the same length and the same warp marker positions ([CDM](https://cdm.link/live-12-3-arrives/); [Live 12 manual, Stem Separation](https://www.ableton.com/en/manual/stem-separation/)). The Live 12 release notes also say Live "will now correctly restore warp markers in long samples when those samples are imported into a Set", which implies earlier 12.x builds could lose them; the exact build of the fix is not pinned down ([Live 12 release notes](https://www.ableton.com/en/release-notes/live-12/)).

This raises a real risk for separated stems. Live analyzes each clip on its own. A vocal or bass stem has sparser onsets than the full mix, so its tempo or downbeat guess can be worse, and stems from one song can end up with slightly different warp maps. That follows from per-clip analysis, but no one has measured it. The fix is manual and documented. Use "Set 1.1.1 Here" at the first downbeat, then "Warp From Here". Or type the known tempo into the clip's Seg. BPM field with Warp on. Or use "Warp From Here (Start At …)", which uses "the tempo of the Set as a baseline for auto-warping" ([Live 12 manual](https://www.ableton.com/en/manual/audio-clips-tempo-and-warping/); [Ableton Help](https://help.ableton.com/hc/en-us/articles/209772085-Setting-exact-BPM-values-in-the-Arrangement-View)). Ableton's own stems article and a forum tip boil down to one approach: set the global tempo to the song's BPM first, and turn auto-warp off for stems that are already aligned ([Ableton Help](https://help.ableton.com/hc/en-us/articles/360000843404); [Ableton forum](https://forum.ableton.com/viewtopic.php?p=1745335)). OpenStems stems all start at sample 0 and have the same length. Unwarped stems at a Set tempo equal to the song's tempo therefore line up with each other and with the grid, apart from the offset before bar 1.

No source shows a macOS and Windows difference in how Live treats WAV metadata or auto-warp. The platform differences found concern Live's own stem separation speed and M4A import, which is Mac only ([Live 12 release notes](https://www.ableton.com/en/release-notes/live-12/); [Live 12 manual: files](https://www.ableton.com/en/live-manual/12/managing-files-and-sets/)). Nothing in this report has been tried in Live on the owner's M1 Max, or on Windows.

## .asd files carry warp markers, but only Live can write them

A `.asd` is Live's per-sample analysis cache. It has the sample's name plus `.asd`, sits beside the sample, and holds data for stretching quality, tempo detection of long samples and fast waveform drawing. It is written on first import when "Create Analysis Files" is on, which is the default, and a sample that has one is not analyzed again. **Save Default Clip** also stores the clip's warp markers, warp on/off, start/end, loop, gain and pitch in it. The sample then loads with those settings whenever it is added to any Set, and **"When a sample is saved with Warp Markers, Auto-Warp will have no effect"** ([Live 12 manual: files](https://www.ableton.com/en/live-manual/12/managing-files-and-sets/); [Live 12 manual: warping](https://www.ableton.com/en/manual/audio-clips-tempo-and-warping/)). Live's export dialog can also write a `.asd` for rendered audio. Sample packs ship them; the Analog Drums manual, for example, says each WAV comes with an Ableton `.asd`. So a copied `.asd` beside the same WAV is accepted on another machine ([Analog Drums manual](https://d3eqtkjnkd3tai.cloudfront.net/misc/Analog+Drums+-+Manual.pdf)). In principle, then, a `.asd` with its first warp marker at beat 0 on the downbeat and a second marker at the song's tempo would give Live both bar 1 and the tempo.

In practice a third party cannot write one. The format is undocumented binary. The only public parser, DBraun's AbletonParsing, reads Live 9 and 10 files, misreads some Live 10.1 and 11 files on both macOS and Windows, and says that **"Ableton Live 12 uses a different binary format that is not yet supported"** ([AbletonParsing](https://github.com/DBraun/AbletonParsing); [issue #1](https://www.github.com/DBraun/AbletonParsing/issues/1)). Asked to generate `.asd` files from rekordbox or Traktor beat grids, its author replied: "This project is not capable of producing .asd files because I have no idea how to" ([issue #3](https://www.github.com/DBraun/AbletonParsing/issues/3)). Live 11.3 re-analyzed existing files for its new auto-warp ([Ableton forum](https://forum.ableton.com/viewtopic.php?p=1813790)). How Live decides a `.asd` still matches its sample is unknown. The only evidence is a 2007 forum thread, where shortening an audio file by 1 ms dropped its warp markers ([Ableton forum](https://forum.ableton.com/viewtopic.php?p=549965)). A hand-written file would most likely be thrown away and re-analyzed without any sign, and a partly accepted one could put a stem on the wrong grid with no error. No sample tool, DJ tool or stem service was found writing `.asd` files from scratch. The tools that hand Live a grid write a Live Set instead. DJ.Studio's stems export, for one, is "a .zip file with a .als file in it" that opens "with their beat grid" ([DJ.Studio help](https://help.dj.studio/en/articles/9616541-export-stems-to-ableton-live)).

## A generated Live Set is the one route that carries bar 1

An `.als` is gzip-compressed XML. Real sets show the pieces OpenStems would need. The song tempo is `<Tempo>…<Manual Value="143"/>` in the main track's mixer. Each `AudioClip` has a `SampleRef/FileRef` pointing at the file and a `<WarpMarkers>` block of `<WarpMarker SecTime="…" BeatTime="…"/>` pairs, where SecTime is seconds into the file and BeatTime is beats from the clip's start ([Ableton forum](https://forum.ableton.com/viewtopic.php?p=1383377); [aesthetic.computer notes](https://tangled.org/aesthetic.computer/core/blob/main/docs/ableton-als-structure.md)). With two markers, Live reads the tempo between them as beats ÷ (seconds/60). OpenStems already has both inputs: the song's BPM and the time of the first downbeat, including any tempo the user typed in by hand. Each stem's clip would get `SecTime = downbeat, BeatTime = 0` and a second marker far along at `SecTime = downbeat + n·60/bpm, BeatTime = n`. Bar 1 then lands on 1.1.1, and any pickup sits at negative beats. A song with a varying tempo would need more markers, which only matters if detection ever produces a tempo map.

The format is undocumented, so the safe way to build it is the one the only working open generator uses. suno-to-ableton starts from a set saved by real Live, patches the tempo and the clips' file references, and warns that output must be checked in Live, not only by unit tests ([suno-to-ableton](https://steven-ahfu.github.io/suno-to-ableton/als-export)). Element names such as `IsWarped`, `CurrentStart` and `NextPointeeId` come from secondary or general knowledge, so confirm them by diffing a set saved in Live. Live opens sets from older versions but not newer ones; Live 11 will not open a Live 12 set ([Ableton Help](https://help.ableton.com/hc/en-us/articles/360000841004); [Ableton forum](https://forum.ableton.com/viewtopic.php?p=1835799)). So a template saved in Live 11 reaches both versions, and Live 12 asks for Save As. For Mac and Windows the one difference that matters is the file path inside the set. A set written into the stems folder with relative references should open on both systems and survive the folder being moved, though no source compares how the two systems encode paths in a set. A Live Clip (`.alc`) is the same XML family for a single clip ([Live manual](https://www.ableton.com/en/manual/managing-files-and-sets/)), but a Set does strictly more. A Max for Live device could do the same job live. The Live Object Model offers `create_audio_clip`, `warping` and `add_warp_marker` ([Cycling '74 LOM Track](https://docs.cycling74.com/apiref/lom/track/); [Cycling '74 LOM Clip](https://docs.cycling74.com/apiref/lom/clip/)). But it needs a Live edition with Max for Live, the user has to load the device, and the version that added `create_audio_clip` is unverified.

## Six tests in Live would settle the open questions

Every claim above about the current Live comes from documents. None was tried on the owner's machines. These tests take an afternoon. Each test should run on Live 12.4 under Windows and on the M1 Max, and on Live 11 where it is installed.

| Test | How | Settles |
|---|---|---|
| Acid chunk | One stem at an unusual tempo (e.g. 97 BPM) written with and without the acid chunk, and once with beat count N instead of 0; import each with Auto-Warp Long Samples on and off and read Seg. BPM | Whether Live ignores the chunk, as Ableton's help says |
| File name | The same stem named `… 97bpm.wav` | Whether the name changes the estimate (expected: no) |
| Auto-warp across stems | Drop all stems of one song at once, auto-warp on, and compare the first marker and Seg. BPM per stem | Whether stems of one song get different grids, and whether multi-clip "Set 1.1.1 Here" (12.3+) is available for them |
| Hint workflow | Set tempo first, warp off; then warp on with Seg. BPM typed | That the recommended wording gives aligned stems |
| Minimal `.als` | A Live 11 template patched with tempo, two stems, two warp markers each, relative paths; open in Live 11 and 12 on both systems, then move the folder | Whether a generated set opens, lands bar 1 at 1.1.1, and survives a move |
| `.asd` staleness (optional) | Save Default Clip on a stem, then touch, copy or re-write the WAV | How Live binds a `.asd` to its sample, closing the door on option 6 for good |

## Conclusion

The FL Studio path doesn't carry over. FL reads the acid chunk's tempo; Live reads nothing from the file and guesses from the audio. That makes Live's result depend on how well its analysis handles a thin stem, which is the weakest material it can get. OpenStems, though, holds exactly what Live lacks: a tempo and a bar 1 from the full mix, before separation. The value for Live users lies in handing over that knowledge, not in another tag. Today that means a hint that shows the numbers. Later, if the six tests come back as expected, it means a generated Set that places them as warp markers. That would put OpenStems ahead of the tools surveyed, which leave Live users to set the tempo themselves. Ableton's own stem separation sidesteps the problem only because its stems are made inside Live.

Building the Set is a commitment to checking Live releases, so it should wait until the acid test confirms the headline. It should also wait until the auto-warp test shows real drift between stems. If Live's 11.3.10+ analysis already places one marker on the right downbeat for every stem, the hint alone may be enough.
